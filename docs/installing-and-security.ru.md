# Установка, релизы и локальные данные

[English](installing-and-security.md) · [Русский](installing-and-security.ru.md) · [简体中文](installing-and-security.zh-CN.md) · [Документация](README.ru.md)

## Обновление приложения

Первую версию со встроенным механизмом обновления нужно установить вручную. Последующие обновления берутся из стабильных релизов `howdeploy/CanvasTTY`. macOS сохраняет ad-hoc подпись приложения и использует отдельную Ed25519-подпись архива Sparkle. Для выпуска нужен подписанный appcast и закрытый ключ владельца релиза.

Владелец релизов задаёт в GitHub Actions репозитория `howdeploy/CanvasTTY` переменную `SPARKLE_PUBLIC_ED_KEY` и секрет `SPARKLE_EDDSA_PRIVATE_KEY`. Оба значения — base64 представление 32-байтовых публичного ключа и закрытого seed одной пары Sparkle. Закрытый ключ не хранится в репозитории. CI проверяет соответствие ключей, встраивает публичный ключ в macOS-приложение, подписывает `appcast.xml` и ZIP и до публикации проверяет стабильный тег и полноту файлов.

При сборке macOS в CI для pull request используется тестовый публичный ключ, если переменная владельца недоступна; такие пакеты не публикуются как релиз. Перед публикацией стабильного релиза отдельный job также сверяет имена, размеры и SHA-512 файлов с метаданными обновления.

### Однократная настройка подписи Sparkle для мейнтейнера

На доверенном Mac используйте инструменты закреплённой версии Sparkle 2.10.0 и установленный GitHub CLI (`gh`) с авторизацией. `generate_keys` сохраняет закрытый ключ в login Keychain; `--account` отделяет ключ CanvasTTY от ключей других организаций. Сделайте защищённую резервную копию ключа. Используйте одну пару для следующих релизов: приложение с уже встроенным публичным ключом не сможет проверить обновление, подписанное другой парой, без запланированной ротации ключа или ручной переустановки.

```bash
npm ci
npm run build:mac-updater
gh auth status
artifacts/sparkle/distribution/bin/generate_keys --account howdeploy.CanvasTTY
gh variable set SPARKLE_PUBLIC_ED_KEY --repo howdeploy/CanvasTTY \
  --body "$(artifacts/sparkle/distribution/bin/generate_keys --account howdeploy.CanvasTTY -p)"
(
  umask 077
  key_dir="$(mktemp -d)"
  trap 'rm -f "$key_dir/private.key"; rmdir "$key_dir"' EXIT
  artifacts/sparkle/distribution/bin/generate_keys --account howdeploy.CanvasTTY -x "$key_dir/private.key"
  gh secret set SPARKLE_EDDSA_PRIVATE_KEY --app actions --repo howdeploy/CanvasTTY < "$key_dir/private.key"
)
```

После слияния PR с обновлениями выполните эти команды один раз до создания первого релизного тега, используя GitHub-аккаунт с правом настройки Actions variables и secrets в `howdeploy/CanvasTTY`. Экспортированный seed существует во временном файле только во время загрузки; не коммитьте его и не используйте тестовый публичный ключ для релиза. Проверьте наличие обоих имён в **Settings → Secrets and variables → Actions**. Перед подписью Mac-обновления release job проверяет соответствие ключей. Само слияние PR релиз не публикует: его запускает тег `vX.Y.Z`. Ручной `workflow_dispatch` только собирает пакеты.

## Пакеты для пользователей

Каждый тег `v*` запускает нативные сборки на раннерах GitHub для всех трёх ОС:

| Платформа | Артефакты | Примечания |
|:--|:--|:--|
| Linux x86_64 | AppImage, deb | AppImage — однофайловый пакет, которому нужна библиотека совместимости FUSE 2 (`libfuse2t64` в Ubuntu 24.04); deb интегрируется с окружениями рабочего стола семейства Debian |
| Windows x64 | NSIS-установщик, portable-исполняемый файл | Установщик позволяет выбрать каталог и создаёт ярлыки в меню «Пуск» и на рабочем столе |
| macOS arm64 (Apple Silicon) | dmg, zip | Оба содержат графический бандл `.app`; сборки для Intel/x64 отсутствуют |

Скачивайте файлы только со страницы [GitHub Releases](https://github.com/howdeploy/CanvasTTY/releases) этого репозитория. Начиная с `1.2.4`, бандлы macOS подписываются ad-hoc и перед загрузкой проходят строгую проверку `codesign`. Это подтверждает целостность бандла, но не предоставляет Developer ID и notarization Apple, поэтому Gatekeeper может потребовать Finder → Open или Privacy & Security → Open Anyway. Пакеты Windows остаются неподписанными и могут вызвать предупреждение SmartScreen. Артефакты macOS из `1.2.2` и `1.2.3` созданы до этого исправления подписи; используйте `1.2.4` или новее. Прежде чем подтверждать предупреждение, сверьте тег релиза и имя файла.

## Что входит в сборку

В `electron-builder.yml` задан явный белый список: продакшен-бандлы из `out/`, `package.json`, MIT `LICENSE` и необходимые production-зависимости. Документация из исходников, `.env`, локальные каталоги agent/planning, логи, настройки, учётные данные и рабочие файлы релиза в пакет не копируются.

`node-pty` пересобирается на соответствующем раннере GitHub, поэтому пакеты для Linux, Windows и macOS получают нативный модуль под свою ОС. Сборка одной ОС никогда не выдаётся за сборку другой.

## Пользовательские данные — только локально

| Данные | Где хранятся и как долго |
|:--|:--|
| Настройки CanvasTTY | Пользовательский каталог Electron `userData` (`~/.config/canvastty` на типичном Linux-десктопе, `%APPDATA%\canvastty` в Windows, `~/Library/Application Support/canvastty` в macOS) |
| Учётные данные провайдеров | Локальное хранилище установленного CLI Codex, Claude, Qwen Code, Kimi, OpenCode, Hermes или Grok Build; CanvasTTY его не копирует |
| Временный browser bridge провайдера | Fallback-записи Kimi и MCP-запись Hermes журналируются, принадлежат только активным сессиям CanvasTTY и восстанавливаются при завершении последней PTY или после прерванного запуска; capability-секреты никогда не записываются литералами |
| PTY scrollback | Ограниченный буфер в памяти main-процесса на время запущенной сессии приложения; в репозиторий не сохраняется |
| Медиа на домашнем экране | Исходный локальный файл пользователя; в настройках хранится только локальный путь к нему |
| Runtime-плагины | Статические пакеты и реестр включения в `userData/plugins`; изолированное JSON-хранилище в `userData/plugin-storage` ограничено 64 КБ на плагин и удаляется при uninstall |
| Секреты плагинов | Зашифрованные blobs в `userData/plugin-secrets`; plaintext доступен только владеющему включённому плагину через permission-gated вызовы, без защищённого шифрования ОС запись завершается ошибкой, а файл удаляется при uninstall |
| Разрешения на медиапапки | `userData/plugin-media-libraries.json`; содержит абсолютные пути явно выбранных пользователем каталогов и удаляет разрешения плагина при uninstall |
| Плейлисты плагинов | Плагин с подтверждённым правом записи может создавать ограниченные файлы только в каталоге `Playlists/` выбранной медиабиблиотеки |
| Профиль встроенного браузера | Cookies, cache и site storage в постоянном Electron-разделе `canvastty-browser`; в `1.0.2` браузер доступен из HOME |
| Restore state браузера | Безопасные HTTP(S) URL вкладок, их порядок и active-tab ID в `userData/browser-state.json`; выключается/очищается вместе с восстановлением вкладок |
| Журнал аудита браузера | Очищенный hash-chain JSONL в `userData/browser/audit`; активный файл ротируется при 100 МБ, а ротированные файлы старше 30 дней удаляются при инициализации или следующей ротации store |
| Остальные логи | Только локальные stdout/stderr; у CanvasTTY нет ни удалённого сборщика логов, ни собственного эндпоинта телеметрии |

Точный путь `userData` зависит от конфигурации ОС. CanvasTTY запрашивает у Electron правильный пользовательский каталог и никогда не использует клон исходников как хранилище во время работы.

## Граница учётных данных

Учётные данные провайдера читаются только в доверенном main-процессе, когда их требует запрос квоты, опирающийся на реальный источник. Они отправляются только на соответствующий эндпоинт этого провайдера, не логируются, не сохраняются CanvasTTY и никогда не пересекают типизированный preload-мост. Loopback-токен Kimi остаётся в памяти процесса, а stderr его дочернего процесса отбрасывается.

По IPC могут передаваться только очищенные данные: проценты, метаданные окна квоты, метки времени и явные причины недоступности. Сырые ответы провайдера, bearer-заголовки, cookies и файлы с учётными данными — не могут. Секреты runtime-плагинов образуют отдельную opt-in границу: они проходят только по request path владеющего sandbox при наличии `secrets` в manifest и шифруются на диске через Electron `safeStorage`.

## Защита репозитория

```bash
npm run audit:secrets
npm test
```

Аудит проверяет характерные форматы токенов провайдеров и облачных сервисов, блоки приватных ключей, жёстко прописанные в коде присваивания секретов, чувствительные имена файлов и абсолютные пути к домашним каталогам. Имена repository metadata исключаются до определения типа entry, поэтому игнорируются и обычный каталог `.git/`, и `.git`-файл linked worktree, но personal path в публикуемом файле по-прежнему обнаруживается. `.gitignore` исключает локальный контекст агента, данные планирования, env-файлы, учётные данные, логи, настройки, зависимости и сгенерированные пакеты. CI запускает аудит перед сборкой, а каждая release-задача — ещё раз перед упаковкой.

Ни один сканер не идеален. Не коммитьте действующий секрет даже «на минутку». Если он попал в историю Git, сначала отзовите его, а потом вычистите историю до публикации репозитория.

## Локальная сборка пакетов

```bash
npm install
npm run package
```

`npm run package` создаёт распакованное приложение для текущей ОС. Платформенные скрипты создают установщики:

```bash
npm run package:linux
npm run package:win
npm run package:mac
```

Запускайте каждый скрипт на соответствующей ОС. Кросс-компиляция не считается доказательством совместимости, потому что `node-pty` — нативный модуль.

## Чек-лист релиза

1. Убедитесь, что переменная и секрет Sparkle настроены в `howdeploy/CanvasTTY`; не создавайте новую пару для каждого релиза. Сверьте SemVer в `package.json` и теге.
2. Запустите аудит секретов, тесты, typecheck, продакшен-сборку и сборку пакета для текущей ОС.
3. Проверьте настоящее упакованное приложение и белый список содержимого пакета.
4. Проверьте обновление кандидатных пакетов на реальных устройствах с Linux, Windows и macOS.
5. Отправьте `vX.Y.Z` и дождитесь всех трёх package-задач в GitHub Actions. После проверки файлов workflow сразу публикует тег как стабильный релиз.

Browser storage, доступ агентов и retention журнала описаны в руководстве [Встроенный браузер и журнал аудита](browser.ru.md). Сообщения об уязвимостях принимаются согласно [политике безопасности](../SECURITY.ru.md) репозитория.
